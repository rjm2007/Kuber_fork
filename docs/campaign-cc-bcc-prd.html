01

Feature Overview

Campaign-level CC / BCC adds two optional address lists to a master campaign. When Kuber creates or patches Instantly sub-campaigns during send fan-out (or config sync), those lists are passed as Instantly cc_list and bcc_list.

Instantly then CCs / BCCs those addresses on every sequence email for every lead under that Instantly campaign. Managers configure this once in campaign Options — the same place as sender name, window, and daily limit — not inside each lead draft.

Create / Edit campaign → set CC / BCC lists → approve drafts → send fan-out → Instantly sub-campaigns get cc_list / bcc_list → all sequence emails include them

Why Instantly campaign-level (not per email)

Kuber does not send campaign mail through Gmail/Outlook/SMTP APIs. Outreach is Instantly-only. Instantly already exposes campaign-level cc_list / bcc_list on create and patch. Per-message CC only exists today on Unibox reply (cc_address_email_list), which is a different product surface.

02

Problem / Client Use Case

Sales managers often need a fixed stakeholder copied on every campaign outreach email — for example a regional manager, a shared sales inbox, or an internal archive address — without putting that person in the To field or editing every AI draft.

Today Kuber has no way to do this for campaigns:

  • Create / Edit campaign Options expose sender name, schedule, daily limit, HIL, follow-ups, AI context, and attachment — but not CC / BCC. Confirmed — implementation
  • createInstantlyCampaign and patchInstantlyCampaignConfig never send cc_list / bcc_list. Confirmed — implementation
  • Unibox reply API already accepts CC / BCC, but there is no campaign UI and no fan-out wiring. Confirmed — implementation

Without this, internal visibility and compliance copying require manual Instantly console edits (fragile across country/mailbox sub-campaigns) or putting addresses into email bodies (wrong semantics).

03

Goals

  • Allow a manager to set zero or more CC addresses and zero or more BCC addresses on a campaign.
  • Persist those lists on the master campaigns row as source of truth.
  • Pass them to Instantly on sub-campaign create and on live config sync.
  • Apply the same lists to every country / mailbox Instantly sub-campaign created by fan-out.
  • Apply to all sequence steps Instantly sends for that campaign (step 1 + follow-ups).
  • Support edit-before-send and edit-after-send (sync to existing Instantly campaigns), matching how daily_limit works today.
  • Keep UX campaign-scoped — never force CC/BCC into per-lead draft editors.
04

Non-Goals

  • Per-lead or per-draft CC / BCC. Out of scope. Instantly campaign fields are shared across leads.
  • Unibox reply CC / BCC UI. Backend already accepts cc / bcc on POST /api/v1/unibox/reply; exposing that in the reply composer is a separate ticket.
  • Per-step CC / BCC. Instantly applies lists at campaign level, not per sequence step.
  • Different CC / BCC per country or mailbox bucket. V1 uses one shared list from the master campaign for every Instantly sub-campaign.
  • Direct Gmail / Outlook / SMTP send. Campaign outreach remains Instantly-only.
  • Showing CC / BCC inside AI draft subject/body. Recipients stay on Instantly headers, not in personalized copy.
  • Changing who the primary To recipient is. Lead email remains the To address via Instantly lead add.
05

Product Decisions

Decision 1

Scope = Instantly campaign-level lists

Chosen — Campaign-level Proposed Store on master campaign; pass Instantly cc_list / bcc_list. One configuration for the whole campaign.
Rejected — Per-email / Unibox path Reply API fields already exist for one-off threads; they do not cover sequence blast and would require per-message UI.

Matches Instantly’s native model and Kuber’s fan-out architecture (one Instantly campaign per country × mailbox).

Decision 2

Same lists for every sub-campaign

Chosen — Fan out identically Proposed Every Instantly sub-campaign created/patched for this master campaign gets the same CC / BCC arrays.
Deferred — Per-bucket overrides Could live later on instantly_campaigns; adds UI and sync complexity not justified for V1.
Decision 3

Empty means clear / omit

Chosen Proposed Empty arrays are valid. On create, omit Instantly fields when empty. On patch after send, explicitly send empty arrays so Instantly clears prior lists.
Rejected — “Unset” separate from empty No third state; null/empty both mean no CC/BCC.
Decision 4

Visibility of addresses to the lead

CC addresses are visible to the primary recipient (standard email semantics). BCC addresses are not. Product copy in the UI must label them clearly so managers do not put a confidential archive on CC by mistake.

User Flow

1

Create campaign

Proposed

In Create Campaign → Options (near Sender name), manager optionally adds CC and BCC addresses. Lists save with the campaign on create.

2

Edit before first send

Proposed

Edit Campaign updates the master row only. No Instantly call yet if no sub-campaigns exist — same pattern as other pre-send Options.

3

Send approved leads

Confirmed — implementation

sendCampaign() buckets leads by country × sender mailbox, creates Instantly campaigns if needed, adds leads, activates. New Instantly campaigns include cc_list / bcc_list from the master campaign.

4

Edit after send / while active

Proposed

Config PATCH updates master DB, then patches every linked Instantly sub-campaign’s cc_list / bcc_list (same fan-out pattern as schedule / daily limit).

Already-sent emails

Changing CC / BCC does not rewrite messages Instantly already delivered. It only affects future sequence sends / remaining steps. Surface this in Edit UI helper text.

5

Read-only config view

Proposed

Campaign config modal / drawer summary shows CC and BCC chips (or “None”) so viewers without edit permission can still see who is copied.

07

UI Requirements

7.1 Placement

Add two fields under campaign Options in:

  • create-campaign-modal.tsx
  • edit-campaign-modal.tsx
  • Read-only display in campaign-config-modal.tsx (and drawer summary if Options are mirrored there)

Place below Sender name (same Options section). Fields sit on bg-card panels, so inputs must use bg-background per the surface ladder.

7.2 Control design Proposed

CC

  • Label: “CC”
  • Multi-email chip input or comma/Enter-to-add list
  • Helper: “Visible to the lead on every campaign email.”

BCC

  • Label: “BCC”
  • Same control pattern as CC
  • Helper: “Hidden from the lead. Applied to every campaign email.”
  • Max addresses per list: 10 (soft product limit; Instantly docs do not publish a hard max — verify if needed).
  • Inline validation for invalid emails; block Save/Create until fixed.
  • Case-fold + trim + dedupe within each list on save.
  • Do not allow the same address in both CC and BCC (prefer CC, reject BCC duplicate — or reject both; V1: reject with clear error).

7.3 Permissions

Reuse existing campaign Options edit permission (canEditSharedOptions / role gates already on create-edit). No new capability flag for V1.

Database Impact

Proposed Add two columns on public.campaigns:

alter table public.campaigns
  add column if not exists cc_emails  text[] not null default '{}',
  add column if not exists bcc_emails text[] not null default '{}';

comment on column public.campaigns.cc_emails  is
  'Campaign-level CC addresses passed to Instantly cc_list on every sub-campaign';
comment on column public.campaigns.bcc_emails is
  'Campaign-level BCC addresses passed to Instantly bcc_list on every sub-campaign';
  • No new table.
  • No mirror columns on instantly_campaigns for V1 (Instantly is the runtime store; master campaign is Kuber source of truth).
  • Do not reuse unibox_emails.cc_emails / bcc_emails (those are inbound message fields, type text, different lifecycle).

API & Validation

11.1 Schemas

Extend CreateCampaignSchema and PatchCampaignSchema in lib/validators/campaigns.ts:

cc_emails:  z.array(z.string().email()).max(10).optional()
bcc_emails: z.array(z.string().email()).max(10).optional()

Plus a refine: no address appears in both lists; normalize trim + lowercase before persist.

11.2 Routes

RouteChange
POST /api/v1/campaigns Accept + persist cc_emails / bcc_emails
PATCH /api/v1/campaigns/[id]/config Accept + persist; if Instantly sub-campaigns exist, patch each with cc_list / bcc_list
GET campaign / drawer payloads Return the new fields so UI can hydrate
POST …/send No new body fields — fan-out reads from DB

11.3 Instantly client

// createInstantlyCampaign
{ ..., cc_list?: string[], bcc_list?: string[] }

// patchInstantlyCampaignConfig
{ ..., ccList?: string[], bccList?: string[] }

Scalars patch independently (like daily_limit). Unlike campaign_schedule, no read-merge required for list replacement — send the full arrays when provided.

14

Acceptance Criteria

  1. Create campaign with CC and BCC addresses; values persist and reload in Edit / config views.
  2. Create campaign with neither list; send path behaves identically to current production.
  3. On first send, Instantly campaign create payload includes the configured cc_list / bcc_list for every country × mailbox sub-campaign.
  4. Delivered test email shows CC / BCC headers matching the campaign lists (subject to Instantly account rules — see §15).
  5. Edit lists on an already-sent campaign; subsequent Instantly sequence emails use the new lists; already-sent messages unchanged.
  6. Clearing both lists patches Instantly to empty and future sends have no CC/BCC.
  7. Invalid emails, >10 addresses, or overlapping CC/BCC are rejected by API validation with a clear error.
  8. Users without Options edit permission cannot change the lists; they can still view them if the config UI is visible.
  9. Unibox reply UI remains unchanged (no accidental scope creep).
15

Open Business Questions

BQ-1 · Blocking

Must CC / BCC be Instantly workspace “accounts”?

Instantly docs describe the fields as “List of accounts…”. If only connected sending accounts are accepted, the UI should be a multi-select of sending accounts rather than a free-text email chip input.

Owner: Engineering verification on Instantly sandbox · Blocks: final UI control choice
BQ-2

Default CC for all new campaigns?

Should company settings gain a default CC / BCC that pre-fills new campaigns (e.g. always BCC a compliance inbox)?

V1 proposal: No defaults — opt-in per campaign. Defaults can be a follow-up.
BQ-3

Should replies also auto-CC?

Campaign lists do not automatically apply to Unibox manual/AI replies. Do managers expect reply threads to keep the same CC?

V1 proposal: No. Document as non-goal; optional later using existing reply API fields.
BQ-4

Hard max addresses?

Is 10 enough for the client’s regional manager + archive use case?

V1 proposal: Cap at 10; raise later if Instantly allows and client needs more.
16

Implementation Notes

  • Normalize emails once at the API boundary; UI and Instantly both receive the normalized arrays.
  • Prefer passing lists only when defined on Instantly create; always pass full arrays on patch when the config endpoint is updating them so clears work.
  • Keep logging: when Instantly rejects a list, include Instantly error body in the existing campaign error path (last_error / API error), not a silent drop.
  • No change to draft generation, certification, or lead CRM status machine.
  • Respect existing UI surface contrast: field fills bg-background on bg-card panels.

18

Implementation Readiness

Ready to implement after BQ-1

Architecture is clear: store on campaigns, pass Instantly campaign fields in fan-out and config sync, expose in Options UI. No new provider integration. Estimated surface is small (migration + validators + Instantly client + fan-out + 2–3 modals).

Do not ship UI copy until verified

If Instantly rejects arbitrary emails, switch from free-text chips to a multi-select of Instantly sending accounts before release.

Suggested build order: Instantly smoke test (BQ-1) → migration → Instantly client → fan-out → config PATCH sync → validators/API → UI → acceptance test on a real mailbox.
